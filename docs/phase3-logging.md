## Loki vs ELK Comparison
Why did we choose Loki over ELK (Elasticsearch, Logstash, Kibana) for this project?

1. **Resource Efficiency (Instance Size):** ELK is incredibly powerful but very resource-hungry. Elasticsearch uses a heavy JVM and requires significant RAM (often 2GB+ just for ES) and CPU to index full-text data. Loki, on the other hand, only indexes labels (like Promtail extracting `service="backend"`) and leaves the actual log lines unindexed. This makes Loki extremely lightweight, fitting perfectly onto a smaller, budget-friendly EC2 instance alongside the app stack without risking out-of-memory crashes.
2. **Timeline & Simplicity:** Logstash is notoriously complex to configure with GROK patterns. Promtail seamlessly hooks into the Docker socket out-of-the-box and requires minimal configuration to extract labels from Docker container metadata. This allows us to set it up quickly and meet our 2-day deadline without over-engineering.
3. **Native Grafana Integration:** Since we already use Grafana for Prometheus metrics, Loki integrates seamlessly. We can view metrics and logs on the exact same dashboard without needing Kibana as a separate UI.

## Verification Steps

### 1. Generating an Error
You can manually generate an error by sending a bad request to the ML service (e.g., missing fields in a crop request):
```bash
# SSH into your EC2 instance and run a bad request
curl -X POST http://localhost:5001/predict/crop \
  -H "Content-Type: application/json" \
  -d '{"N": 10}'
```
*(Or, run the Phase 2 `traffic.py` script which automatically generates bad requests.)*

### 2. Finding the Error in Grafana Explore
1. Open Grafana (`http://<EC2_IP>:3000`).
2. Click the **Explore** icon (a compass) on the left sidebar.
3. In the datasource dropdown at the top-left, select **Loki**.
4. In the **Label filters** builder:
   - Label: `service`
   - Operator: `=`
   - Value: `ml_service` (or `backend`)
5. In the **Line contains** input, type `error` or `Exception`.
6. Alternatively, switch to the "Code" view and type the LogQL query directly:
   `{service="ml_service"} |= "error"`
7. Click **Run query** (top right). You will instantly see the exact error logs generated by the bad crop request.

### 3. Checking the Dashboard
1. Go to **Dashboards -> Farmer Helper Logs**.
2. Verify you see the **Log Volume by Service**, which should plot lines for `backend`, `frontend`, and `ml_service`.
3. Verify the **Error Logs Volume** panel registers spikes.
4. Verify the **Live Logs** feed populates with the raw docker logs.
